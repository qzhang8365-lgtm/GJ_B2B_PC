# 业务方接入验收清单

本文件面向**业务开发同学**：当你基于本设计 skill 提供的共享资产（`assets/styles/gj-b2b-tokens.css`、`gj-b2b-components.css`、各 `assets/scripts/*.js`）手写业务页面时，用这份清单在提交/联调前自查一遍。

不同于仓库里其他 `references/*.md`（那些是给生成规范页/组件的 AI 用的内部规则），这份文件专门收录**业务页面接入共享基座时的常见翻车模式**——每一条都来自真实审计中发现、并已在 `references/audit-tracker.md` 里有据可查的问题，不是凭空列举的"最佳实践"。

## 核心原则

共享组件（尤其带 JS 交互的：DatePicker、Selector、Table 等）通常已经把状态同步、可访问性、视觉联动都处理好了。业务页面**只应该驱动组件暴露出来的接口**（赋值给它监听的输入框、派发它监听的事件、调用它导出的方法），而不是绕开组件自己去操作 DOM 视觉细节。凡是业务代码里出现"手动改一段本该由共享脚本负责的文字/class/样式"，都值得停下来检查是不是在重复造轮子，并且大概率漏掉了什么。

## 已知翻车模式（提交前逐条自查）

### 1. 表单标签宽度不要写死成小于最长文案的固定像素值

**症状**：同一个筛选表单里，字数多的标签（比如"通话时长（秒）："“归属营业部："）文字被挤到贴住相邻输入框，冒号看不清甚至消失；字数少的标签则正常，间距和对齐都好看。

**原因**：给 `.gj-form-label-horizontal` 写了类似 `flex:0 0 80px;min-width:80px` 这种固定宽度，只按多数标签的字数估算，没有覆盖到当前表单里实际最长的文案；组件基座本身对标签是 `white-space:nowrap` 且不做任何裁切，超宽的文字会直接溢出到相邻元素上，不会自动换行或被裁掉，所以问题不会"看起来还凑合"，而是很明显地穿帮。

**自查方法**：
- 摆完一行的所有标签后，找出字数最多的那一个（含冒号），确认写死的宽度 ≥ 它在 14px 字号下的实际渲染宽度（可以在浏览器里选中文字用 devtools 量，或者直接把这一行所有标签都换成同一个足够宽的固定值）。
- 更稳妥的做法：不要写死 `flex:0 0 <px>`，改成 `flex:0 0 auto;min-width:<px>`（只设一个保底最小宽度，不限制上限），让长文案自己撑开，短文案仍然按 `min-width` 对齐，视觉上不会错乱。
- 如果暂时改不了 CSS，最快的临时办法是缩短这几个标签的中文文案（比如去掉"（秒）"这种可以用 placeholder 表达的补充信息）。

**已知真实案例**：业务方「呼叫中心录音查询」页面，"通话时长（秒）：""归属营业部：" 两个标签溢出（`references/audit-tracker.md` 相关条目见 2026-09-28 审计记录）。

### 2. 程序化设置组件默认值，要走组件监听的事件，不要直接改 DOM 文字/样式

**症状**：某个交互组件（典型是 DatePicker）明明已经有一个有意义的默认值在生效，但视觉上却是"未选择/占位符"的浅灰色，用户容易误以为这个筛选条件根本没生效。

**原因**：业务 JS 在页面初始化时，直接给组件的底层输入框赋值、又手动改了触发器上文字节点的 `textContent`，但共享组件自己真正维护"当前是否有值、要不要切换高亮态"的逻辑是**监听输入框的 `change` 事件**触发的——直接赋值不会自动派发 `change`，导致组件永远不知道值变了，视觉状态也就永远停在初始态。

**自查方法**：
- 打开对应组件的共享脚本（比如 `assets/scripts/gj-date-picker.js`），搜索它监听了哪些事件（`addEventListener('change', ...)`）、或者有没有导出可调用的方法。
- 业务代码里凡是"程序化"（不是用户真的点了组件 UI）去设置这个组件的值，都要用触发同一套事件的方式去做，而不是直接操作组件内部的文字节点或 class。最简单的写法：
  ```js
  input.value = 新值;
  input.dispatchEvent(new Event('change', { bubbles: true }));
  ```
  然后让组件自己的监听逻辑去更新视觉，业务代码不用、也不应该自己再写一遍"该显示什么颜色/文字"。
- 提交前实际操作一遍页面：默认值刚加载出来时的视觉状态，应该和用户手动选择同一个值之后的视觉状态**完全一致**（同样的文字颜色、同样的高亮 class）。如果两者不一样，说明默认值没有走组件正常的更新路径。

**已知真实案例**：业务方「呼叫中心录音查询」页面，"通话日期"默认的"最近30天"区间用了灰色占位态文字（`references/audit-tracker.md` 相关条目见 2026-09-28 审计记录）。

### 3. 需要数字输入时，用 `.gj-number-input` 组件包裹，不要用原生 `<input type="number">`

**症状**：数字输入框右侧带一个原生浏览器自带的上下小箭头（不同浏览器/系统样式不统一，和设计系统里其余控件的视觉基座完全不一致）；如果业务代码沿用给其他输入类组件加错误态类的方式（直接给 `<input>` 加 `gj-form-error`），校验失败时也不会有任何红框提示。

**原因**：设计系统里数字输入的规范组件是 `.gj-number-input`（外层 `<label>` 包裹一个不带 `type="number"` 的普通 `<input>`），原生浏览器小箭头（spinner）从未被这个组件采用；同时组件的边框是画在外层 `<label>` 上、不是内部 `<input>` 上，所以给内部 `<input>` 加错误态类不会有视觉效果。

**自查方法**：
- 搜索页面里是否还有 `<input type="number">`——设计系统里任何需要输入数字的场景都应该是 `<label class="gj-number-input"><input ...></label>` 这种结构，没有 `type="number"`。
- 如果这个字段需要校验失败时的红框提示，确认错误态类是加在外层 `.gj-number-input` 元素上（比如 `input.closest('.gj-number-input')`），而不是内部 `<input>` 上。

**已知真实案例**：业务方「呼叫中心录音查询」页面，"通话时长（秒）"最小值/最大值两个原生 `type="number"` 输入框（`references/audit-tracker.md` INN-006）。

### 4. 同一栅格里标签长度不一致时，用右对齐/边缘对齐，不要只加宽标签列再左对齐

**症状**：给标签列统一加宽到能容纳最长文案后，字数少的标签和输入框之间留出一大段不自然的空白，看起来"间距太大"。

**原因**：标签容器加宽是为了不溢出，但如果标签内文字本身仍然是默认的左对齐，短文案自然会贴着容器左边，离右边的输入框就远了。Form 组件规范页里"边缘对齐"的展示明确是：不同长度的标签应该**贴着输入框对齐**（也就是标签内文字右对齐/靠近输入框一侧），而不是贴着标签列的左边界对齐。

**自查方法**：
- 参考 `preview/form/index.html`（或规范页里"边缘对齐"截图）核对视觉：同一栅格里，不同长度的标签，末尾（冒号）应该在同一条竖线上对齐，而不是开头对齐。
- 给标签容器加 `justify-content:flex-end;text-align:right`（配合固定宽度或 `min-width`），而不是只加宽度。

**已知真实案例**：业务方「呼叫中心录音查询」页面，标签列加宽到 112px 解决溢出后，短标签左对齐导致视觉间距不均（`references/audit-tracker.md` 相关条目，2026-09-28 审计记录）。

### 5. 给 page-patterns 里已经用 flex `gap` 布局的容器手动加 margin 调间距，会跟 gap 叠加导致间距翻倍

**症状**：业务页面反馈某处间距"看起来还是偏松"，改小了 margin 数值、甚至已经按公式换算过应该对应多少像素，但页面实际渲染出来的间距和改动前几乎没变化，或者比预期大出一截；用 devtools 量出来的实际间距，比业务组合层 CSS 里写的 margin 值大，且差值正好等于父容器的 `gap` 值。

**原因**：`page-patterns.css` 里不少页面级布局容器本身就是 `display:flex` + `gap:<N>px`（例如查询表单容器 `.query-filter{display:flex;flex-direction:column;gap:16px}`，以及 `.toolbar`/`.actions`/`.row`/`.query-list-card` 等也都设了 `gap`），`gap` 已经统一负责了这些容器的直接子元素之间的间距。如果业务组合层（`xxx-gj.css`）又给这些直接子元素额外写了 `margin-top`/`margin-bottom` 来"调整行距/间距"，margin 不会被 gap 覆盖或吸收，两者是叠加关系，实际间距 = gap + margin，比预想的大得多；而且业务同学此时如果只按"这个间距应该是多少"去改小 margin 数值，永远改不到位，因为总有一份来自 gap 的固定间距没被看见。

**自查方法**：
- 改任何"行间距/区块间距"之前，先确认目标元素的**父容器**有没有继承 page-patterns.css 里带 `gap` 的类。确认方法：devtools 选中父元素看 Computed 面板里的 `display` 是不是 `flex`/`grid`、`gap` 是多少；或者直接在 page-patterns.css / gj-b2b-components.css 里搜这个父容器的类名。
- 如果父容器已经有 `gap`：间距调整应该改 `gap` 本身（可以用更具体的选择器覆盖，比如 `.recording-query-page .query-filter{gap:12px}`），不要再给子元素加 margin。只有父容器不是 flex/grid（没有 gap 机制，子元素靠普通文档流堆叠）时，才用子元素自己的 margin 控制间距。
- 不要只在 CSS 源码层面核对"我写的数字对不对"，改完之后一定要在渲染出来的页面里实测相邻两个元素的实际像素间距（用脚本量 `getBoundingClientRect().top` 的差值，或者 devtools 直接量），跟源文件/设计稿的实测值做比较——光看自己写的 margin/gap 数值"理论上应该是多少"，不能替代实际渲染结果的核对，两套间距机制叠加在一起时尤其容易算错。

**已知真实案例**：业务方「呼叫中心录音查询」页面，`.query-filter` 表单容器本身有 `gap:16px`，业务组合层又给筛选行加了 `margin-top:12px`，实际行间距变成 16+12=28px（而不是预期的 12px），第一轮"收紧间距"因此没有明显效果；业务同学（Sally）反馈"调整之后还是不够紧凑"，实测 `getBoundingClientRect` 才定位到是两套间距机制叠加，而不是数值改得不够小（`references/audit-tracker.md` 相关条目，2026-09-28 审计记录）。

### 6. 同一页面里语义相同的"卡片/区块标题"，字号要跟 skill 标准值保持一致，不要各自估一个数字

**症状**：同一个页面里两个视觉角色相同的标题（都是卡片/区块的一级标题）字号不一样，用户一眼能看出不协调，但对着 CSS 代码分别看很容易忽略——因为两处都写了"看起来合理"的 `font-weight:600`，只是具体 px 数值不同。

**原因**：skill 里像 `.query-list-title{margin:0;font:600 16px/24px}` 这样的标题样式，是给走标准 `query-list-card`/`query-list-toolbar` 结构的区块用的、可以直接复用的 class。但如果业务页面里另一个区块走的是自定义结构（没有复用 `query-list-card`），业务组合层就得自己写一条 `.xxx-title{...}` 规则——这条规则很容易凭感觉估一个字号（比如误用了页面里其他地方的标签字号），而不是去核对 skill 里"卡片标题"这个语义角色本身的标准值，就会出现同一页面里标题级别不统一的问题。

**自查方法**：
- 页面里凡是语义为"卡片/区块一级标题"的文字，不管是否直接复用了 `.query-list-title` 这样的现成 class，字号/字重/行高都应该跟 skill 里其它卡片标题保持一致（当前标准是 `600 16px/24px`）。
- 如果这个区块没法直接复用 `.query-list-title`（结构不同、外层容器不是 flex-gap 布局），就把这三个值原样抄进业务组合层自己的标题规则里，不要凭印象估数字。
- 提交前把页面里所有卡片标题截图并排放在一起比对，或者写个小脚本把所有标题元素的 `font-size`/`font-weight`/`line-height` 打印出来比对——正常滚动浏览页面时反而不容易注意到 1~2px 的细微不统一。

**已知真实案例**：业务方「呼叫中心录音查询」页面，"通话统计"标题用了业务组合层自己写的 `.recording-stats-title{font:600 14px/22px}`，跟"通话详情"标题复用的 skill 标准 `.query-list-title{font:600 16px/24px}` 不一致；业务同学（Sally）发现两个标题字号不一样后追问原因，定位到是业务组合层这条规则字号写错了，已改成一致的 `16px/24px`（`references/audit-tracker.md` 相关条目，2026-09-28 审计记录）。

### 7. 共享组件本身就有的插槽（Logo/公告等），不要在组件外面另起一个自定义容器去实现，会多出一整行

**症状**：页面顶部（或其它复用了 Navbar/Header 一类共享组件的位置）看起来变成了两行，源文件里明明是一行；业务组合层自己加了一个 `div` 放品牌名/公告文案，跟下面紧挨着的共享组件（比如 `gj-navbar`）各占一整行分开渲染。

**原因**：像 Navbar 这样的共享组件，schema/rules 里已经把 Logo、公告（Bulletin）定义成组件自身"从左至右"功能区里的一部分（跟搜索框、通知图标、用户入口、退出按钮同属一行），组件的 CSS 也已经有现成的 `.gj-navbar-logo`/`.gj-navbar-bulletin` 类可以直接用。如果业务同学没意识到这些插槽已经存在，就会另外写一个业务专属的容器（比如 `.recording-host-bar`）来"手动实现"品牌名+公告，再把它摞在组件上面——这样两块各自成一行，总高度变成组件本身高度的两倍，跟源文件的单行布局对不上。

**自查方法**：
- 往共享组件（Navbar、Header 之类）里加内容之前，先看这个组件的 `rules.md`/`schema.json` 有没有已经定义好的插槽/属性能覆盖这个需求（比如 Navbar 的 `Logo`/`Bulletin`/`LogButton`），不要想当然地在组件外面另起容器。
- 组件文档里如果已经给出了标准 DOM 结构示例（class 名、嵌套关系），直接照抄这份结构放进组件内部，不要只抄视觉效果自己重新拼一份 markup。
- 改完之后量一下承载这块内容的组件外层容器的整体高度，跟组件 schema 里写的标准高度（比如 Navbar 的 60px）核对，如果实测高度明显偏高（比如翻倍），大概率就是多加了一层不该有的容器。

**已知真实案例**：业务方「呼叫中心录音查询」页面，顶部品牌名「综合服务管理平台」和公告文案被放进了业务自建的 `.recording-host-bar`，摞在 `gj-navbar` 组件上面，导致顶部变成两行；而 `gj-navbar` 组件本身早就有 `.gj-navbar-logo`/`.gj-navbar-bulletin` 现成插槽（`references/components/navbar/schema.json` 里 `Bulletin`/`Logo` 属性），业务同学（Sally）发现两行布局不合理后定位到是没有复用这两个插槽，已改成把品牌名和公告文案放进 `gj-navbar` 内部，恢复成源文件的单行布局。

## 提交前自查清单

- [ ] 本页所有表单标签，都用最长的实际文案量过宽度，没有出现文字贴边/溢出
- [ ] 本页所有"页面加载即生效"的默认值（日期、下拉选中项、勾选状态等），视觉表现和用户手动操作后完全一致
- [ ] 本页没有为共享组件（DatePicker/Selector/Table 等）手写一份"重新实现组件视觉状态"的私有逻辑——凡是组件自带 JS 已经在做的事，业务代码只负责喂数据/触发事件，不重复实现
- [ ] 在至少一个比设计稿窄的常见分辨率（如 1280px）下完整走查过一遍，确认没有元素因为固定像素宽度而互相重叠
- [ ] 数字输入统一用 `.gj-number-input` 组件包裹，没有裸的 `<input type="number">`
- [ ] 同一栅格里长度不一致的标签是贴着输入框对齐（右对齐/边缘对齐），不是贴着标签列左边界对齐
- [ ] 本页调整过的行/区块间距，都确认过父容器是不是已经用 `gap` 布局（flex/grid），没有出现子元素 margin 和父容器 gap 叠加导致间距变大
- [ ] 本页所有卡片/区块一级标题的字号字重行高一致（标准值 `600 16px/24px`），没有业务组合层自己估出来的不同数值
- [ ] 本页用到的共享组件（Navbar/Header 等）如果需要加 Logo/公告一类内容，确认过组件本身有没有现成插槽，没有在组件外面另起业务自建容器
