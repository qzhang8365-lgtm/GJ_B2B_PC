# 组件规范页面制作约束

## 图标资源

- 页面中的图标必须优先引用 `assets/icons/iconfont/` 中已经上传的组件库资源。
- General 通用图标引用普通 SVG / Icon Font 资源；复杂渐变效果图标引用对应 Effect SVG 资源。
- 不使用 Emoji、Unicode 符号、临时 CSS 图形或自行绘制的替代图标。
- 图标默认跟随相邻文字颜色；需要继承颜色时，可将组件库 SVG 用作 CSS mask，但资源来源仍必须是已上传图标库。
- 只有组件库确实不存在所需图标时，才提出缺失项并等待补充，不自行创造近似图标。

## 组件基座与死代码

- 预览页的静态展示区和交互 Demo 区，都必须使用共享 `assets/styles/gj-b2b-components.css` 里的标准组件类（`gj-modal`、`gj-modal-close`、`gj-btn`、`gj-form-*` 等）渲染，不允许另起一套仅供该页面使用的 mock 结构（例如自定义的 `.icon-button`、`.modal-window`、`.btn` 等）——这类临时结构一旦被真实组件类替换后忘记清理，会在页面内嵌 `<style>` 里留下死代码，增加后续误改的风险（2026-09-11 起，MDL-010 首次系统性核查并清理）。
- 迁移或重构某个预览页的展示结构后，必须回头检查该页 `<style>` 里是否还有不再被任何 `class="..."`（含 JS 拼接的模板字符串）引用的选择器；复合选择器（如 `.a,.b{...}`）要逐项核对，只删除全部子选择器都确认无引用的规则，混有真实类的要保留但裁掉死亡分支，不整条删除。
- 不确定某个类是否还在用时，先在真实 HTML/JS 里搜索确认，不凭选择器名称是否眼熟就删除或保留。

## 展示背景选择

- 默认使用白色展示背景（`docs-surface-white`）：适合组件自身带灰色填充、或默认态就是深色/强对比色的组件（如 Tabs、Selector、Input、灰底按钮组、卡片）。
- 灰色背景（不带修饰类的 `docs-stage` 默认态，或显式 `docs-surface-gray`）按需使用：主要用于展示白色或近似白色填充的组件——例如 Checkbox/Radio 默认态是白底 + 描边，直接放在白色画布上会被边框以外的部分"吃掉"，需要灰色画布制造至少一级明度差；同理适用于阴影、悬浮卡片，以及其他需要与页面白底区分的内容。
- 深色或透明组件使用专用对比背景（`docs-surface-dark`）：例如 Ghost 按钮、白色半透明填充、Glass 效果，选择能清楚体现边界的深色或图案背景。
- 展示背景与组件默认填充之间必须保持至少一级明度差，不能让组件容器与演示画布融为一体；两者恰好都是白色时，用 `docs-surface-white` 自带的 1px 边框而不是改变背景色来建立边界。
- 判断明度差时要看「实际相邻的两层」，不要只按组件类型套用固定背景色：如果演示区本身已经用一张卡片（sample-card、combo-card、interaction-stage、controls 之类的私有容器）承担了「白色/灰色展示面」的角色，外层 docs-stage 该选什么色要看这张卡片的颜色，而不是看卡片里最终渲染的组件颜色——卡片是白色就配灰色画布，卡片是灰色就配白色画布，避免同色卡片叠同色画布导致内外边界消失（Input 页面 INP-010 就是先套用了「Input 默认应配白色画布」的字面规则、忽略了页面已有白色卡片这一层，导致两层白色叠在一起，后来改回灰色画布才修正）。
- 交互演示区的属性控制面板（`.controls`）固定使用 `docs-surface-white`，与左侧 `.lab` 演示舞台的背景选择规则相互独立。
- 背景只服务于辨认组件本身，不应暗示组件在实际业务页面中必须运行于该背景上。

## 展示区的网格布局

- 一组并排展示的变体（尺寸、状态、类型……）优先用显式 `display:grid` 加固定 `grid-template-columns` 列数，不要用 `display:flex;flex-wrap:wrap` 让浏览器按容器宽度自然换行——flex-wrap 换行的结果随视口宽度变化，同一组内容在 1280px 和 1000px 下可能是不同的换行方式，看起来「参差不齐」（Switch/DatePicker 的 SWI-005/DTP-013 曾因此被用户反馈「矩阵不整齐」）。
- 选列数时优先让列数能整除卡片数（例如 6 个状态用 3 列或 2 列，不用 4 列留一个孤项）；确实除不尽、必须有孤项时，让它落在明确的网格末尾（比如 2 列网格最后一行只有 1 项），而不是因为容器宽度不够才被动换行到下一行——同一份 HTML 在不同宽度下应该呈现同一个结构，只在预设的窄屏断点才整体切换列数。
- 如果一组展示天然是两个维度的组合（例如尺寸 × 状态），做成真正的表格（行 = 一个维度，列 = 另一个维度），不要拆成一串卡片再指望它们自然换行拼成矩阵——像 Input 的「尺寸与状态」`state-table` 那样显式表达两个维度，比 8 张卡片挤成 2 行 4 列更可靠，也是用户认可的参照样式。
- 单个变体宽度差异很大时（例如 DatePicker 的单日期面板 280px vs 范围面板 560px），用显式的 `grid-column:1/-1`（或等效 span）让宽项跨列，而不是让 flex-wrap 按剩余空间随意决定它跟谁同行。

## 交互脚本与元素显隐

- 不要用 `el.hidden = true/false`（或 `hidden` 属性）来控制共享组件基座类（如 `gj-btn`、`gj-btn-primary` 等）元素的显隐——这些类自身在 `gj-b2b-components.css` 里显式声明了 `display:inline-flex` 之类的值，是作者样式表规则，会覆盖浏览器对 `[hidden]` 属性的默认 `display:none`（同优先级下作者样式表本就压过 UA 样式表，与选择器权重无关），导致元素设置 `hidden` 后实际仍然可见、照常占位（Search 页面 SEA-005 曾用 Playwright 的 `getComputedStyle` 实测复现：`button.hidden=true` 后 `display` 仍是 `flex`）。
- 正确做法是直接控制 `el.style.display`（例如 `el.style.display = condition ? 'none' : ''`），或者切换一个页面私有的、优先级更高的显隐类；`hidden` 属性只适用于没有被组件基座显式设置 `display` 的普通容器元素。
- 这是一个可能残留在其他预览页的共性问题（例如 Upload/Toast 页面也用 `.hidden` 切换 `gj-btn` 按钮），后续任何页面被审计到交互脚本时，应顺带检查是否存在同样的写法。
